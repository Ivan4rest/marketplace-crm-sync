# Синхронизация заказов маркетплейса с CRM

Демо-проект: сервис, который переносит заказы с маркетплейса в CRM как сделки, держит их статусы в актуальном состоянии и отправляет обратно остатки товаров.

*Marketplace → CRM order sync (Python, httpx, SQLite): incremental order import, idempotent deal upsert, status mapping, stock sync back to the marketplace, safe retries after failures.*

## Что умеет

- **Забирает только изменения.** Запоминает, до какого момента заказы уже обработаны, и запрашивает только новые и изменённые, постранично.
- **Не создаёт дубли.** Связь «заказ → сделка» хранится в базе; если сбой случился между созданием сделки и сохранением связи, сделка находится в CRM по номеру заказа.
- **Обновляет статусы.** Статус заказа переводится в этап сделки по таблице соответствия.
- **Переживает сбои.** Заказ, который не удалось передать, запоминается и передаётся при следующем проходе; остальные заказы при этом не задерживаются. Если недоступен сам маркетплейс, проход пропускается без изменений состояния.
- **Синхронизирует остатки** из CRM на маркетплейс, отправляя только изменившиеся позиции.

Маркетплейс и CRM в демо учебные (папка `mock_services`). Обращения к внешним системам собраны в `ordersync/clients.py`: чтобы подключить Ozon, Wildberries, amoCRM или Битрикс24, переписываются методы двух классов, логика синхронизации остаётся прежней.

## Запуск

```bash
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt   # Linux/macOS: .venv/bin/pip
```

В одном терминале запустите учебные сервисы:

```bash
.venv/Scripts/uvicorn mock_services.app:app
```

В другом — синхронизацию:

```bash
.venv/Scripts/python -m ordersync
```

Пример вывода трёх проходов (между вторым и третьим вызван `POST /demo/advance`, имитирующий новый заказ и смену статусов):

```
Заказы: создано 3, обновлено 0, без изменений 0, ошибок 0
Остатки: отправлено 3
Заказы: создано 0, обновлено 0, без изменений 1, ошибок 0
Остатки: отправлено 0
Заказы: создано 1, обновлено 3, без изменений 0, ошибок 0
Остатки: отправлено 1
```

Сделки видны на http://localhost:8000/crm/deals. Для постоянной работы: `python -m ordersync --every 60`.

## Настройки

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `MARKETPLACE_URL` | `http://localhost:8000/marketplace` | Адрес API маркетплейса |
| `MARKETPLACE_TOKEN` | — | Токен доступа (заголовок `Authorization`) |
| `CRM_URL` | `http://localhost:8000/crm` | Адрес API CRM |
| `CRM_TOKEN` | — | Токен доступа |
| `STATE_DB` | `state.db` | Файл состояния |

## Тесты

```bash
.venv/Scripts/pip install pytest
.venv/Scripts/python -m pytest
```

Тесты проверяют, в частности, отказ CRM посреди прохода, потерю связи после создания сделки и недоступность маркетплейса.

## Устройство

| Файл | Назначение |
|---|---|
| `ordersync/clients.py` | Клиенты маркетплейса и CRM |
| `ordersync/sync.py` | Логика синхронизации заказов и остатков |
| `ordersync/state.py` | Курсор, связи и очередь повторов в SQLite |
| `mock_services/app.py` | Учебные маркетплейс и CRM |

## Ограничения демо

- Обмен идёт опросом по расписанию; если маркетплейс умеет присылать уведомления, их стоит использовать для мгновенной передачи.
- Статус синхронизируется в одну сторону: из маркетплейса в CRM.
- Проход выполняется в один поток; при больших объёмах обращения к CRM стоит распараллелить с учётом её лимитов.
